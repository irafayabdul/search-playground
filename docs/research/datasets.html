Search Dataset Verdict

Nine candidate datasets for the hybrid-search demo and the upcoming evaluation session, scored against five hard constraints. Two research agents; every load-bearing number re-checked on primary sources.

Verdict

Primary — ESCI, US-small slice, enriched with ESCI-S (both Apache-2.0). The only candidate that clears all five bars at once: 29,844 real Amazon queries with 601,354 graded E/S/C/I judgments — the raw material NDCG needs — over products with measured-rich text (median 851 chars), cuttable to laptop size along query boundaries.

Runner-up — WANDS (Wayfair, MIT): 43k products, 480 queries, 233k dense judgments, <100 MB, zero friction. The fallback if ESCI feels heavy.

Already built — Appliances (McAuley) stays as the interactive demo corpus; it has no queries, so it cannot carry the evaluation session alone. Kaggle UK is retired: no judgments, title-only text.

Final call: Abdul — pending.

The join problem — and why ESCI-S, not McAuley

The obvious idea — enrich ESCI queries with the McAuley metadata we already use — mostly fails on a key mismatch: ESCI's product_id is a variant-level ASIN, McAuley collapses to parent_asin.

Measured, not assumed

Empirical join test: of 94,327 Appliances parent ASINs, just 1,767 matched ESCI-US-large product IDs — 771 in US-small. Per-category overlap is inherently tiny; no overall overlap fraction is documented anywhere. Our freshly built Appliances index therefore cannot serve as the judged corpus.

The proven route is ESCI-S (Apache-2.0): a purpose-built scrape of the actual ESCI ASINs covering 1.66M of 1.81M products (91.5%), adding price, stars, ratings count, category tree, and attributes. Shortcut if we want zero joins: metarank/esci ships ESCI + ESCI-S pre-merged, also Apache-2.0.

Load plan (primary path)

  1. Pull examples.parquet (49 MB) and products.parquet (1.03 GB) from amazon-science/esci-data; start ESCI-S from its 10 MB sample before the 3.4 GB full dump.
  2. Qrels = rows with product_locale == "us" and small_version == 1; for development keep split == "test" → 8,956 queries / 181,701 judgments / 164,900 products (or sample 3,000 queries → 58,554 products, ≈ 35 min embedding).
  3. Corpus = products joined on those IDs; embed title + bullets + description, title first — the 256-token window truncates the tail.
  4. Stream ESCI-S, keep matching ASINs, parse display strings ("4.3 out of 5 stars" → 4.3) into the existing must/should/range filter fields.
  5. Map E/S/C/I → gains (paper: 1.0/0.1/0.01/0.0; common: 3/2/1/0) and score NDCG@10 / recall@100; train/test split comes free for the loss-function session.

Verification record

High — exceptionally so. All 12 load-bearing claim clusters checked out: every README/API number matched verbatim on the primary source, all seven HTTP file sizes were byte-exact (ESCI examples/products parquets, WANDS three CSVs, McAuley two category files, MS MARCO collection, ESCI-S S3 dump), and every 'computed locally' figure — US-small label distribution, test-split slice, unique-product counts, and the decisive ESCI-vs-McAuley Appliances join overlap (1,767/771) — reproduced exactly when I re-downloaded the data and recomputed independently. No claim was found wrong. Unchecked residue is minor and non-decisional: text-richness medians (would need the 1 GB products download; everything around them reproduced), Home Depot and TREC details (both marked non-picks by the research itself), and the Kaggle 131 MB zip figure. Two nuances worth carrying forward: (1) the ESCI-S dump is 3.62 decimal GB (3.37 GiB), so budget ~3.6 GB, and (2) the McAuley dataset is best described as 'no license at all' rather than 'non-commercial' — the card states no usage terms, only a citation request. The recommendation's factual basis (ESCI+ESCI-S primary, WANDS runner-up, direct McAuley join infeasible at scale) is fully supported by the verified evidence.
