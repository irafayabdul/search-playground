Search Tooling Landscape

Thirty-six free and open-source tools across six layers of the search stack, licenses read from the actual LICENSE files — mapped against the OpenSearch pipeline we already run.

Verdict

Our stack is the textbook 2026 stack in miniature. The industry-standard pattern for e-commerce search — a Lucene-based engine running BM25 + dense k-NN hybrid, RRF fusion, a cross-encoder reranker, sentence-transformers embeddings — is exactly the shape already built. Nothing about it is off-standard; nothing needs replacing.

Add for the evaluation session: ranx (metrics + significance tests + a reference RRF to check ours against) and Quepid (collect our own judgments against the live index). Avoid: NAVER SPLADE (non-commercial license), standalone vector DBs (redundant with OpenSearch k-NN), and framework retrieval layers that hide the mechanics we're teaching.

Premise check — “Elasticsearch is not open source”

Needs a 2024-shaped update: since 8.16 (Aug 2024), Elasticsearch core is triple-licensed — AGPL-3.0-only or SSPL-1.0 or Elastic License 2.0 — and AGPL-3.0 is OSI-approved, so the core formally is open source again (verified in the repo's LICENSE.txt).

Two caveats keep OpenSearch the right call anyway: the x-pack tree — including much of the ML/semantic tooling such as ELSER — stays ELv2-only, so “free Elasticsearch” means per-feature license auditing; and AGPL copyleft makes some companies nervous for anything network-served. OpenSearch is uniformly Apache-2.0 under Linux Foundation governance. The accurate line for the session: “open source again, but single-vendor, partly ELv2-gated, and copyleft — OpenSearch remains the clean fully-Apache choice.”

What to add, in priority order

  1. ranx (MIT) — Qrels/Run objects, NDCG@k / MAP / MRR / recall, paired significance tests between pipeline variants (BM25-only vs k-NN-only vs RRF vs reranked is a ready-made lesson arc), and ranx.fuse to sanity-check our hand-rolled RRF.
  2. Quepid (Apache-2.0) — docker-compose, points at the existing OpenSearch; the three of us judge 20–30 queries and the metrics session runs on our own labels.
  3. ir_datasets + BEIR's small sets — instant corpus/queries/qrels while our own judgments are thin.
  4. Server-side fusion — OpenSearch 2.19 already ships hybrid query + normalization / score-ranker (RRF) processors; compare against our client-side RRF as a live eval exercise.
  5. ONNX export (optional) — quantized all-MiniLM-L6-v2 via optimum/onnxruntime for roughly 2–3× CPU embedding speed.
  6. OpenSearch neural-sparse (stretch) — the legally clean SPLADE-family retriever (Apache-2.0 models on HF), wired into the native neural_sparse query.
