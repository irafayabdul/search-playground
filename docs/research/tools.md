# Open-Source Search Tooling — Landscape

*Researched 2026-08-22 (scout + adversarial license-verifier). All 14 claims confirmed on primary sources.*

## Elasticsearch licensing status

The user's claim needs a 2024-shaped correction: since Elasticsearch 8.16 (announced 29 Aug 2024), core Elasticsearch and Kibana are TRIPLE-licensed — your choice of AGPL-3.0-only, SSPL-1.0, or Elastic License 2.0 — and AGPL-3.0 is OSI-approved, so Elasticsearch core is formally open source again (verified in the repo's LICENSE.txt: "The default throughout the repository is a triple license... GNU Affero General Public License v3.0 only, the Server Side Public License v1, and the Elastic License 2.0"). Two caveats keep our OpenSearch decision correct anyway: (1) the x-pack folder — which contains much of the ML/semantic tooling such as ELSER — remains Elastic License 2.0 ONLY, i.e. not open source, so 'free Elasticsearch' requires per-feature license auditing; (2) AGPL's copyleft obligations make some companies nervous for anything network-served, whereas OpenSearch is uniformly Apache-2.0 under Linux Foundation governance with zero per-file checking. Sources: https://github.com/elastic/elasticsearch/blob/main/LICENSE.txt , https://www.elastic.co/blog/elasticsearch-is-open-source-again , https://opensource.org/license/agpl-v3 . So the accurate line for the session is: "Elasticsearch core is open source again (AGPL option since late 2024), but it is single-vendor, partly ELv2-gated, and copyleft — OpenSearch remains the clean fully-Apache choice."

## Verdict

### The industry-standard stack

For e-commerce search in 2026 the industry-standard pattern is exactly the shape we built: a Lucene-based engine (Elasticsearch or OpenSearch; Vespa at the ranking-heavy high end — Vinted/OTTO/Yahoo; 'Postgres-as-search' via pgvector/ParadeDB at the low end) running BM25 + dense k-NN hybrid retrieval fused with RRF or score normalization, followed by a cross-encoder reranker, with embeddings from sentence-transformers-family models; learned-sparse (SPLADE-family / ELSER / OpenSearch neural-sparse) is the mainstream upgrade path on the lexical side; evaluation is offline NDCG/MRR on explicit human judgments (Quepid-style workflows) plus online interleaving/AB — pytrec_eval-derived tooling throughout. Our OpenSearch 2.19 + all-MiniLM-L6-v2 + RRF + ms-marco cross-encoder pipeline IS the textbook 2026 stack in miniature; nothing about it is off-standard.

### What we should add

Add, in priority order: (1) ranx (MIT) — the eval workhorse for next session: Qrels/Run objects, NDCG@k/MAP/MRR/Recall, paired statistical significance tests between pipeline variants (BM25-only vs k-NN-only vs RRF vs reranked — a ready-made lesson arc), plus ranx.fuse to sanity-check our hand-rolled RRF against a reference implementation; (2) Quepid (Apache-2.0, docker-compose, points at our existing OpenSearch) — collect real human judgments from the three collaborators on 20-30 queries so the metrics session runs on our own labels, demonstrating the industry-standard label-collection workflow; (3) ir_datasets + BEIR's small datasets for instant corpus+queries+qrels while our own judgments are thin; (4) move fusion server-side with OpenSearch's hybrid query + normalization/score-ranker (RRF) processor — already in 2.19 — and compare against our client-side RRF as a live eval exercise; (5) optional perf win: export all-MiniLM-L6-v2 to quantized ONNX via onnxruntime/optimum (MIT) for roughly 2-3x CPU embedding speedup; (6) optional stretch: OpenSearch neural-sparse encoder (Apache-2.0 on HF, e.g. opensearch-neural-sparse-encoding-doc-v2-distill) as a third, legally-clean SPLADE-family retriever wired into OpenSearch's native neural_sparse query.

### What to explicitly not adopt

Do NOT adopt: (1) NAVER SPLADE code/weights — CC-BY-NC-SA-4.0 is non-commercial + ShareAlike, wrong for a shared GitHub repo (use OpenSearch's Apache-2.0 neural-sparse models instead); (2) any standalone vector DB (Qdrant/Weaviate/Chroma/Milvus/LanceDB) — OpenSearch k-NN already does this job, a second store fragments the demo, and Milvus specifically is too heavy for a 16 GB laptop; (3) LangChain/LlamaIndex as the retrieval layer — their abstractions hide exactly the fusion/rerank mechanics we are teaching (revisit as thin glue only for the later RAG session); (4) ZincSearch — repository archived, project dead; (5) ScaNN — no macOS arm64 wheels, unusable on this hardware; (6) Annoy — maintenance-mode, obsoleted by HNSW; (7) switching to Elasticsearch — its AGPL option makes it open source again, but it stays single-vendor with ELv2-only x-pack features, and buys us nothing over the OpenSearch cluster already running; (8) RRE — dormant Java tooling superseded by Quepid + ranx.
