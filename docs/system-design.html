Search Playground · system design & roadmap

The Search Blueprint

The complete system in one place: every stage from raw corpus to ranked answer, every contract in the indices, the full data graph, the measured evaluation — and the road ahead, from training our own models to the GraphRAG convergence. This is the A-to-Z design diagram asked for in the 23 Aug session — retrieval and evaluation built and measured, query understanding and serving designed, every model call counted throughout.

github.com/irafayabdul/search-playground @ dad095a corpus: ESCI 482,060 · Appliances 94,313 eval: 150-query sample of 8,956 judged second revision · 29 Aug 2026
The short answer

The funnel is built and measured. OpenSearch 2.19 runs BM25 and HNSW k-NN side by side; Reciprocal Rank Fusion merges them; a cross-encoder re-orders the shortlist. On a 150-query sample of the 8,956 judged ESCI test queries, the pipeline's story is quantified: hybrid beats either retriever alone (+8% NDCG@10 over BM25), reranking is the single largest win (+26.5%), and — the number that frames everything next — 33% of relevant products never enter the top 100 at all. No reranker can recover them.

Next is training the retriever. Both models are off-the-shelf: a MiniLM bi-encoder that has never seen a product catalogue, truncating 42% of the corpus at 256 tokens, and an MS-MARCO cross-encoder transferring from web passages. The ESCI train split — 20,888 queries, 419,653 judgments — is already on disk for exactly this. The loss function decides what the retriever becomes: that is the next session.

The re-ranker is the cheap half of that work and it comes first. Fine-tuning the cross-encoder needs no re-embed — the index is untouched — so it can ship in a day against the same training triples. Fine-tuning the bi-encoder invalidates all 482,060 vectors and forces a full rebuild. Phase 3 below is split accordingly: build the data once, train the re-ranker, then train the retriever.

After that, the two roads converge: serving hardening (the query-understanding front end, caching, server-side RRF, ONNX/Triton, learned-sparse retrieval), and the GraphRAG project — where this search stack becomes the retrieval tool an agent calls.

Two design points carry the stage. RRF fuses on rank because BM25 scores are unbounded and corpus-dependent while cosine lives in [-1,1] — normalising them is guesswork; rank position is comparable by construction. The k-NN filter lives inside the knn clause so OpenSearch applies it during traversal and keeps walking until k documents survive — outside, a selective filter silently returns fewer than k.

Where re-ranking runs — and why not in OpenSearch

ruled 23 Aug · Rashid's production experience
Built · our own batched call

A — the cross-encoder is a separate stage we control

One model.predict() over all (query, document) pairs in a single batch. "Drop the connection in your head between re-ranking and OpenSearch — for re-ranking you've built a separate service. OpenSearch is basically just a vector DB." That separation is also what lets the retriever and the re-ranker be different models, trained independently — the index was built by the retriever and has no relationship to the cross-encoder at all.

Rejected · OpenSearch's built-in rerank endpoint

B — hand the model id to the cluster and let it re-rank

It runs a loop at batch size one: one query against 128 documents becomes 128 sequential encoder invocations instead of one batch. "Because of that it becomes very, very slow. So we don't use that." The endpoint exists and is convenient; the throughput is not.

Stage 0 — designed, not built

Query understanding: what arrives is not what you search with

Our pipeline assumes the caller hands it a clean query string. Production does not work that way — the same retriever has to serve a big AI search box, a small search bar with separate filter widgets, and a RAG chatbot where the "query" is buried in a paragraph of conversation. Before retrieval runs, two things must be pulled out of that raw text.

The front end the funnel is missing

1–2 small model calls per query · latency-critical, hence small models

  Q->>P: clean query + structured must/should filters
  P->>P: the funnel as built - retrieve, trim, rerank

Why a small model and not a big one: this sits in the latency path of every query. A frontier LLM here costs more than the entire retrieval funnel. The pattern from the session is to distil — use the big model once to label training data, fine-tune something around a billion parameters, and serve that. Rashid's team ended up shrinking the extraction model for exactly this reason. Why canonical forms matter: without them, "Python developer" and "Python engineer" are different queries with different result sets and separate cache entries, and your evaluation set fragments across spellings of the same intent.

Serving — the half of the 23 Aug ask this document owed

Deployment, caching, and the cadence that bounds it

The action item named the components explicitly: "how are you deploying it? Are we putting in any caching, any streaming, any queues?" Nothing below is built here — this is the target shape, drawn from what runs in production on Rashid's side.

the cache that works

Service-level, before the retriever

The query arrives at the main service and is answered from cache before any retriever runs — keyed on the lightly normalised query string, so trivial variations collapse onto one entry. TTL of ten to fifteen minutes, and the reason is not memory pressure: documents are re-indexed several times a day, so the same query legitimately returns different results in the morning and the evening. The TTL is bound to the ingest cadence, not chosen for its own sake.

the cache that cannot work

Why the cross-encoder stage is uncacheable

A cross-encoder score is a function of the pair. Every query arrives with a different candidate list, so the (query, document) pairs are almost never repeated — there is nothing to hit. You can cache the final answer for a repeated query at the service level, but you cannot cache the re-ranking stage itself. This is the same property that makes it unprecomputable at index time.

Three edges carry the design. Loaders → one shape: the funnel is corpus-agnostic because every loader emits the same dict. encoder → every index: the same-model contract — retrain the encoder and every solid edge out of it must be rebuilt. qrels → metrics: evaluation joins the corpus only at scoring time, which is why indexing train-split documents never contaminates the test measurement.

What the built system measures

Four variants, 150 judged queries, one table

The harness, stated: 150 queries sampled with a fixed seed from the 8,956 judged test queries; each variant retrieves k=100; the re-ranked variant runs the cross-encoder over the top 25. These are not the demo funnel's defaults (20 → 12 → 10 → 5) — at 20 candidates a recall@100 number would be meaningless. Read the table as a measurement of the four retrieval strategies, not of the notebook's default fan-out.

What counts as relevant: recall uses the strict reading — Exact-labelled products only. Substitutes and complements carry graded gain in NDCG but are excluded from the recall denominator, so "33% never enter the top 100" means 33% of the exact matches.

And what this kind of measurement is for: these are offline metrics — they guide design decisions before anything ships. A deployed system settles relevance differently, by online A/B testing against real user behaviour. Offline numbers that improve are a reason to run the experiment, not proof the users are better served.

the uncomfortable finding

BM25 beats the vectors here

Product search is structurally lexical — brands, model numbers, exact nouns. The embedding model has never seen a catalogue and truncates 42% of it. Vectors are not automatically better; they are better at particular things, and hybrid still beats both because the two retrievers fail on different queries.

the number that sets the roadmap

recall@100 did not move under reranking

0.6700 with and without the cross-encoder — reranking reorders what retrieval found and never retrieves anything new. The remaining 33% is a retrieval failure, and only a better retriever — Phase 3 — can touch it. Floor, not leaderboard: unjudged docs count as non-relevant.

How training data is prepared — the 23 Aug session, distilled

Two paths to (query, document, label) triples

Training a retriever needs labelled pairs. We have the luxury path today; the production methodology from the session is recorded here because it is the answer whenever the corpus is our own — and it is the same discipline the GraphRAG side uses for entity extraction.

path A · ours today

A benchmark did the labelling

ESCI ships 601,354 human-graded judgments under Apache-2.0. Train split for fitting, test split for the honest number. Zero labelling cost, one caveat: the domain is Amazon's, not ours.

path B · production, no benchmark

Build the labels with an LLM, carefully

Real queries first, synthetic to widen, candidate documents chosen to include hard negatives, labels from a batch-API LLM behind an optimised prompt. The discipline is in the sampling and the prompt iterations, not the model.

Phase 3, in full — the next build

Training our own re-ranker and retriever

Both models in the funnel are strangers to this domain: a MiniLM bi-encoder that has never seen a product catalogue, and a cross-encoder trained on Bing web passages. Everything measured so far is what off-the-shelf gets you. This is the plan to change that — ordered by cost, because the two models are trained independently and only meet at the funnel. The index was built by the retriever; the cross-encoder has no relationship to it at all, which is exactly why the re-ranker can be replaced without touching a single stored vector.

3a

Build the training triples — once, for both models

A cross-encoder and a bi-encoder want the same raw material: (query, document, label). We have two ways to get it, and the honest position is that we should do both — the ESCI path to learn the mechanics on clean labels, the synthetic path because it is what we will need when the corpus is ours.

3a-i · free, available now

From ESCI's judgments

20,888 train queries, 419,653 graded judgments, already on disk — the same parquet, filtered to split=="train". E/S/C/I maps to either gain scale. Positives are the E rows; the S and C rows are ready-made hard negatives, which is the part that is normally expensive to construct. Zero labelling cost, zero new downloads.

3a-ii · the transferable method

Built synthetically, when no benchmark exists

The Path B sequence above, executed: real queries from a log, widened with LLM-generated synthetic queries in the same style, candidates drawn deliberately across the similarity distribution to include hard negatives, labelled by a batch-API LLM behind a prompt refined over 10–20 rounds. This is the path for any corpus of our own — and the same discipline the GraphRAG side uses for entity extraction.

the one idea to take from 3a

Hard negatives are the whole game

A model learns nothing from a negative it can already tell apart. Random negatives are trivially separable — pairing "ice maker" with a garden hose teaches the model a distinction it already makes. The distinctions retrieval actually needs live near the decision boundary: the substitute that is almost right, the complement that shares vocabulary but not intent. That is why the sampling reaches into ranks 500–600 and 900–1000 rather than taking the top hundred and calling the rest irrelevant — and it is why ESCI's S and C labels are worth more than its E labels for training purposes.

Why this ships in a day: the cross-encoder is a pure function of (query, document) evaluated at query time. Swapping it changes RERANK_MODEL in config.py and nothing else — no vectors move, no index is rebuilt, no downtime. What it can and cannot fix: it owns NDCG — the ordering of what retrieval already found. It cannot move recall@100 by a single point, because it never retrieves anything. If the re-ranked NDCG improves and recall does not, that is the system working exactly as designed.

The loss function is the design decision, not a hyperparameter. The choice encodes what you want the retriever to be. Train it to be excellent at candidate generation and let a separate cross-encoder handle ordering, or train it to be decent at both and drop the re-ranker to save its latency. Rashid's team pursued the second deliberately — "we want good retrieval plus good re-ranking from the retriever" — because a cross-encoder is a whole extra layer in the latency path. It is a serving-budget decision expressed as a training objective, and there is no universally right answer.

Phase 4 · The production shape — front end, serving, boosting

4a · Query understanding. The stage-0 front end above: a filter-extraction service and an actual-query extractor, ideally a sub-1B fine-tuned model distilled from a large one, plus canonical-form normalisation. Nothing downstream works on raw chatbot text without it.

4b · Serving and caching. Service-level cache keyed on the normalised query with a TTL bound to the reindex cadence (10–15 min); the ingestion path through a broker rather than one bulk write; an A/B harness, because offline NDCG is a design instrument and online behaviour is the verdict. Also here: the ESCI-S enrichment join (Apache-2.0, 91.5% ASIN coverage) to give the judged corpus the price/rating/category filters it lacks.

4c · Inference hardening. Move fusion server-side (OpenSearch 2.19 ships an RRF score-ranker processor — compare against ours as a live exercise); ONNX-quantise the encoders for 2–3× CPU throughput, or run a real inference server. The transferable warning from the session: dynamic padding (padding=True) makes PyTorch cache a tensor per (sequence-length × batch-size) combination — a leak invisible to Python-level tooling, visible only as container memory climbing for a year. padding="max_length" is the mitigation; a purpose-built runtime handles it for you. Plus OpenSearch neural-sparse as the legally-clean SPLADE-family third retriever, and Quepid pointed at our index to collect our own judgments. Rejected with reasons on record: standalone vector DBs, framework retrieval layers, NAVER SPLADE weights (CC-BY-NC-SA).

4d · Boosting. Named in the session and deliberately deferred — what to boost, whether it attaches to the retriever or post-retrieval, and how to evaluate it against judgments rather than intuition. Our only boost today is the implicit title^2 field weight.
