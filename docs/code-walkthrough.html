1 · The shape of the thing

Roughly 700 lines across nine modules. It only looks like a lot because there are three interchangeable dataset loaders. Everything else is two flows.

index time loader → build_embedding_text → encode → bulk write. Happens once, takes ~90 min for 482k documents.
query time retrieve → trim → rerank → return. Happens per search, takes milliseconds.

The two are joined by exactly one contract: the same embedding model must produce both the document vectors and the query vector. Break that and cosine similarity becomes noise — which is also why fine-tuning the model later forces a full reindex.

2 · Index time — building the haystack

Three loaders, one shape

corpus.py (33 hand-written docs), amazon.py (94k Appliances products), and esci.py (482k judged products) all do the same job: turn a messy source row into one uniform dict.

{
  "id":       "B07VXLVHGL",         # stable, used as the OpenSearch _id
  "title":    "COSTWAY Countertop Ice Maker...",
  "features": "26 lbs per 24h. Ready in 6 mins...",   # bullet points
  "text":     "Full product description...",
  # ...then whatever filter fields that dataset happens to have
}
Why it matters Because every loader emits this shape, nothing downstream knows or cares which dataset is loaded. Swapping corpora is a --dataset flag, not a refactor.

Real data is filthy, so loaders defend against it. amazon.py gets prices as 13.99, "$13.99", "None", or nonsense:

def _parse_price(value) -> Optional[float]:
    if value is None: return None
    if isinstance(value, (int, float)): return float(value)
    s = str(value).strip().lstrip("$").replace(",", "")
    try:    return float(s)
    except ValueError: return None     # unparseable -> absent, never a crash

Building the text to embed

embed.py 
def build_embedding_text(doc: dict) -> str:
    parts = [doc.get("title", ""), doc.get("features", ""), doc.get("text", "")]
    return "\n\n".join(p.strip() for p in parts if p and p.strip())

Three lines carrying two decisions from the call.

Concatenate, don't average Embedding the title and body separately and averaging the vectors yields something that represents neither well. Joining them into one string lets the model attend across both.
Order is a truncation strategy MiniLM reads 256 tokens and silently discards everything after. Title first means the most identifying text survives; the description's tail is what gets eaten.

Silent loss is the dangerous kind, so we count it:

def warn_on_truncation(texts, model_name=EMBED_MODEL) -> List[int]:
    tok = get_encoder(model_name).tokenizer
    return [i for i, t in enumerate(texts)
            if len(tok.encode(t, add_special_tokens=True)) > EMBED_MAX_TOKENS]

On the ESCI corpus that fires loudly: 202,607 of 482,060 documents (42%) exceed the window. That is not a bug to fix — it is a real property of the corpus you should know before trusting a recall number. The fix, when you want one, is a longer-window model.

The schema — where fields earn their place

schema.py

The rule from the meeting: a field belongs in the index only if you will filter, score, or retrieve on it. Columns that serve none of those purposes are weight.

"title":    {"type": "text",                     # analysed -> BM25 can match it
             "fields": {"keyword": {"type": "keyword"}}},   # raw -> exact filters
"brand":    {"type": "keyword"},                 # NOT text: filters need exact terms
"price":    {"type": "float"},                   # numeric -> range queries
"location": {"type": "geo_point"},               # enables geo_distance
"embedding": {
    "type": "knn_vector", "dimension": EMBED_DIM,
    "method": {"name": "hnsw", "space_type": "cosinesimil", "engine": "lucene",
               "parameters": {"m": 16, "ef_construction": 128}},
},
text vs keyword is the most common mistake text is tokenised, lowercased, stemmed — good for prose, useless for an exact filter. keyword is stored raw. Most baffling zero-result queries trace back to this one choice.
m and ef_construction are permanent They live inside the vector field definition and are baked into the graph as it is built. Changing them means a full reindex — which is why create_index has a recreate flag. Only ef_search (an index setting, not a mapping) can be tuned on a live index.

Writing it

ingest.py 
vectors = encode(texts)
return [{**d, "embedding": vectors[i].tolist()} for i, d in enumerate(docs)]
# ...then bulk() writes them in batches
refresh=True is a notebook convenience It makes documents searchable immediately. In production the refresh interval exists precisely to batch that work — forcing it per write collapses indexing throughput.

Note we embed client-side. The alternative Rashid showed is ML Commons: register a model group, deploy the model into the cluster, attach an ingest pipeline so OpenSearch embeds on write. That removes the Python-side model but makes indexing compete with queries for cluster resources. The hook is marked in ingest.prepare.

3 · Query time — the funnel

pipeline.py:run is the spine — read this one first. Each stage is more expensive per document and sees fewer of them; invert that and you are running a cross-encoder over the entire corpus.

Stage 1a — lexical (BM25)

"multi_match": {"query": query,
                "fields": ["title^2", "features", "text"],
                "type": "best_fields"}

title^2 doubles the weight of title matches, encoding a reasonable prior: a term in the title is more about the document than the same term buried in prose. Push the boost too far and every query collapses into title keyword matching.

Stage 1b — neural (HNSW k-NN)

knn = {"vector": encode_query(query).tolist(), "k": k}
if clauses["filter"]:
    knn["filter"] = {"bool": {"filter": clauses["filter"]}}   # INSIDE the knn clause
body = {"size": k, "query": {"knn": {"embedding": knn}}}
The filter placement is the subtle bit Inside the knn clause, OpenSearch applies it during graph traversal and keeps walking until it has k survivors. Filter afterwards and a selective filter silently returns fewer than k — you asked for 10 and got 3, with nothing to tell you why.

Stage 2 — must vs should

must   -> clauses["filter"]   # hard constraint: fail it and the document is GONE
should -> clauses["should"]   # soft preference: fail it and you only lose SCORE

Range and list values are detected automatically, so {"price": {"gte": 1, "lte": 150}} becomes a range query and {"brand": ["Sony", "Bose"]} becomes a terms query.

Stage 1c — fusing the two lists (RRF)

search.py — the most interesting 40 lines in the repo 
for list_idx, (results, weight) in enumerate(zip(result_lists, weights)):
    for rank, doc in enumerate(results, start=1):
        fused[doc["id"]] += weight / (k + rank)          # rank, not score
        contributions[doc["id"]][list_idx] = rank        # who found it, and where

The formula is score(d) = Σ wi / (k + ranki(d)).

Why rank and not score BM25 scores are unbounded and depend on corpus statistics. Cosine similarities sit in [-1, 1]. They are not comparable, and normalising them is guesswork dressed up as maths. Rank position is comparable by construction.
What k = 60 buys you It damps the advantage of the very top positions. The gap between rank 1 and rank 2 becomes small, so a document that both retrievers rank decently beats one that a single retriever adores. That is the entire point of hybrid search.

_ranks is kept on every result so you can see the disagreement — that's the lex_rank / vec_rank column in notebook 02.

Stage 3 — the cross-encoder

pairs  = [(query, build_embedding_text(d)) for d in docs]
scores = model.predict(pairs)
...
doc["_rank_delta"] = doc["_retrieval_rank"] - new_rank    # how far it moved
Why it can't be precomputed A bi-encoder embeds query and document separately — that separation is exactly what lets document vectors be written once at index time. A cross-encoder reads the pair jointly, which is far more accurate and impossible to cache. Cost scales with the number of candidates, so it only ever sees the shortlist.
Don't read the absolute score Those ce=-4.4 / ce=+6.4 values are raw logits calibrated on MS MARCO web passages, not probabilities. Only the ordering is meaningful.

The trace

Every stage appends a StageTrace, which is what prints as:

1. retrieve (hybrid)     20 -> 37    top: B08DHR8J7D, B0BZSF2D2M, B09K3FWPGB
2. trim                  37 -> 12    top: B08DHR8J7D, B0BZSF2D2M, B09K3FWPGB
3. rerank (cross-enc)    10 -> 10    top: B0BRX58THH, B09CGS4X1C, B07VXLVHGL
4. final                 10 -> 5     top: B0BRX58THH, B09CGS4X1C, B07VXLVHGL

Stage 1 can return more than k — that is RRF taking the union of two lists of 20. And notice the top document changes at stage 3: that is the reranker earning its cost.

5 · The ESCI dataset, decoded

Three independent filters select a slice — they are not three datasets.

locale   us / jp / es              -> we use `us`
version  small_version / large     -> `small` is Amazon's official Task 1 subset,
                                      a curated harder task, NOT a random sample
split    train / test              -> the official benchmark division
We index both splits, score only test The split governs which queries you score, not which documents exist. Indexing train-split products gives the test queries a realistic haystack to be found in. Those extra products are unjudged rather than known-irrelevant, so NDCG reads as a floor — standard practice, but don't compare the number to a leaderboard computed over a different corpus.

Nothing in our pipeline was trained on ESCI — BM25 has no learned parameters, MiniLM was pretrained elsewhere, the cross-encoder was trained on MS MARCO — so the test split is clean without holding anything back. The train split matters later, for fine-tuning.

esci.py writes two files: the corpus, and a qrels file mapping each test query to its judged documents with both gain scales:

LABEL_GAIN   = {"E": 1.0, "S": 0.1, "C": 0.01, "I": 0.0}   # the paper's weighting
LABEL_GRADED = {"E": 3,   "S": 2,   "C": 1,    "I": 0}     # the common alternative

E = Exact, S = Substitute, C = Complement, I = Irrelevant. Which gain scale you choose changes absolute NDCG but rarely the ordering of two systems.

Things worth breaking on purpose

  1. Set rrf_k to 1 and re-run a hybrid query. Fusion becomes winner-take-all and the whole benefit of hybrid evaporates — watch documents found by both retrievers lose to a single list's favourite.
  2. Move the filter outside the knn clause in neural_search, then run a selective filter. Count the results: fewer than k, silently.
  3. Reverse the order in build_embedding_text so description comes first, reindex a few thousand docs, and compare neural results. With 42% of ESCI truncating, the difference is real.
  4. Set do_rerank=False and compare the top 5. If the cross-encoder is not changing anything, your retrieval is either already excellent or already broken.
